The prediction model: why it's inaccurate and how to fix it

The model type (XGBoost with probability calibration) is a sensible choice. The problems are upstream of it: the model is fed different inputs in production than in training, some training features see the future, and the reported accuracy is measured in a way that overstates it.

Source: backend/apps/ml_pipeline/ (features, training, inference), backend/apps/core/management/commands/{train_model,generate_predictions,train_from_export,sync_real_data}.py, backend/models/*/metadata.json

How the pipeline works today

  1. Training data: finished matches for seasons 2526, 2425, 2324, 2223, 2122 (the defaults in train_model.py), all leagues.
  2. Features (MatchFeatureBuilder): about 120 columns per match. They cover each team's last 5 and 10 results, venue form, season stats, xG, scoring patterns, head-to-head, rest days, weekend/early/late season flags, bookmaker odds and injuries. Missing values are filled with 0.
  3. Models (ModelTrainer): an XGBoost classifier for home/draw/away (200 trees), an XGBoost regressor for total goals, and a classifier for over 2.5 goals. The last 20% (by date) is held out, and the classifiers are calibrated on that same 20%.
  4. Saving: pickles go to /tmp/models/<version> and S3, a ModelVersion row is created with status active, and every other version is archived. This happens with no comparison against the previous model.
  5. Predicting (MatchPredictor): features are rebuilt for each upcoming fixture, then the three models run. generate_predictions stores home/draw/away probabilities, "confidence" (the top probability) and a predicted score.

A log loss of 1.016 is worse than simply using the bookmaker's implied probabilities. As things stand, the model adds no information over the odds it was trained on. A realistic, well-built target is 52–55% accuracy with log loss at or slightly below the market on top leagues. Consistently beating the bookmaker, which "value bets" require, is hard and needs odds captured at the moment you would bet.

Findings

ML-01CriticalThe model trains with odds on every match but predicts with odds = 0
Where
match_features.py _get_odds_features; fixtures come from football_data_org.py (no odds), while FootballDataProvider.sync_fixtures (which has odds) is never called
Why
Historical rows from football-data.co.uk CSVs almost always include average market odds, and odds are usually the strongest features. Upcoming fixtures come from football-data.org, which provides no odds, so implied_*_prob and odds_* are all 0.0 at prediction time. The trees split on odds values that never appear in training as zero, so live predictions go down branches the training data never reached.
Fix
Pick one of these and use it consistently. (a) Get pre-match odds for upcoming fixtures: football-data.co.uk fixtures.csv already has them for its leagues, and the code exists, or use an odds API. (b) Train one model with odds and one without, and choose per match by whether odds exist. Never feed zeros for "unknown": use NaN plus a has_odds flag.
ML-02HighSeason-stat features either see the future or are always zero
Where
team_features.py _get_season_stats (reads TeamSeasonStats for the whole season)
Why
TeamSeasonStats holds season totals, not as-of-date values. If it is populated, a match from matchday 3 is trained with that team's end-of-season record, which includes the result being predicted and all later results (target leakage). This inflates validation and fails on live matches. If it is not populated (I found no sync code that writes it), these 14 home/away columns are always 0. Both cases are wrong.
Fix
Compute season-to-date stats from matches strictly before match_date (the warmed per-team match list is already in memory), or drop these features.
ML-03HighReported accuracy is measured on the rows used for calibration
Where
trainer.py train_result_model / train_over25_model: _calibrate(..., X_val, y_val), then accuracy_score(y_val, ...)
Fix
Split by time into train / calibration / test (e.g. train ≤ 2024-25, calibrate on 2025-26 first half, test on 2025-26 second half and on 2026-27 so far). Report on the test set only. Track log loss, Brier score, ranked probability score (RPS), accuracy and a calibration curve, each next to the bookmaker baseline.
ML-04HighEvery new model goes live automatically, even a worse one
Where
trainer.py save_models: archives all active versions, then creates the new one as ACTIVE
Effect
The Admin "Train Model" button (--leagues E0 --seasons 2425, about 380 matches) replaces the full multi-league model. A bad daily run is never caught.
Fix
Save new models as evaluating. Promote one only if its test log loss beats the active model on the same test window. Otherwise keep it archived and log why.
ML-05HighA second training path produces models the predictor would read backwards
Where
train_from_export.py
Why
It encodes results as 0 = Away, 1 = Draw, 2 = Home, while MatchPredictor._predict reads proba[0] as home and proba[2] as away. Its 24 feature names (home_ppg, implied_home…) mostly don't exist in the live feature extractor, so they would be filled with 0. It uses a random split, saves with joblib while the loader uses pickle, and creates no ModelVersion row. load_models falls back to "latest directory" when no active row exists, so one of these could be loaded, with home and away swapped. The newest local model directory (20260708_073153) is one of these.
Fix
Delete this command and the export workflow, or make it reuse FeatureExtractor + ModelTrainer. Remove the "latest directory" fallback: no active model should mean no predictions.
ML-06CriticalMany upcoming fixtures belong to "new" teams with no history, so their features are zero
Where
football_data_org.py _find_or_create_team; details in DATA-01
Effect
When football-data.org's name doesn't match the football-data.co.uk name, a new Team row is created. That team has no past matches, so form, venue form, head-to-head and rest days are all empty or default. The model then predicts from the home-advantage prior alone.
Fix
A team alias table plus a one-off merge of duplicates (DATA-01). Then re-generate upcoming predictions.
ML-07Medium"Unknown" is encoded as 0
Where
X.fillna(0) in the trainer, features.get(col, 0.0) in the predictor, and every "no data" default in the feature builders
Why
0 is a real value: 0 points, 0 goals, 0% win rate. XGBoost handles NaN natively and learns the best direction for missing values.
Fix
Leave missing values as NaN end to end, and add count features (matches_in_history, has_odds, has_xg).
ML-08MediumThe predicted score is made up and can contradict the prediction
Where
generate_predictions.py: home = total_goals × 0.55, away = total_goals × 0.45
Effect
Every match shows a slight home lead, even when "Away win" is predicted. For example, the page shows "Predicted: AWAY (1–1)".
Fix
Fit a Poisson or Dixon–Coles goals model (team attack/defence strengths plus home advantage). Its scoreline grid gives a consistent most-likely score, over/under 2.5, both-teams-to-score, and a second home/draw/away estimate to blend in.
ML-09MediumSeason codes are hard-coded and already out of date
Where
train_model.py default seasons; settings.HISTORICAL_SEASONS (stops at 2425); tasks/data_sync.py ('2526'); generate_predictions._generate_historical_predictions ('2526'); retrain_model_task ('2324'…'1920')
Effect
The current season, 2026-27, is excluded from training even though results arrive for it daily.
Fix
One helper, current_season_code(today, start_month), and "last N seasons" computed from it everywhere.
ML-10MediumThe training-data cache can serve old data
Where
feature_extractor.py _get_cache_key (seasons/leagues/groups only), used with use_disk_cache=True
Why
The cache key never changes as new results arrive. On a warm Lambda container, /tmp survives between invocations, and locally backend/cache/features/*.pkl holds four stale datasets. A retrain can silently reuse yesterday's (or last month's) dataset.
Fix
Include the finished-match count and latest updated_at in the key, or turn the disk cache off for scheduled training.
ML-11HighThe accuracy shown in the app is miscounted and can include "predictions" made after the game
Where
api/views/predictions.py stats; generate_predictions --historical; _generate_simple_predictions
Why
(1) total = predictions.count() is taken before skipping matches with missing scores. (2) There is no check that the prediction was created before kickoff. --historical back-fills finished matches using a model trained on those same matches (in-sample), and the fallback "simple" predictor can also label finished matches. (3) Without a trained model, _generate_simple_predictions predicts the league's most common result, "home", for every match.
Fix
Count only predictions with created_at < kickoff. Freeze predictions at kickoff (stop update_or_create once the match has started). Store is_backtest for back-filled rows and exclude them from the headline accuracy.
ML-12MediumPredictions don't record which model made them or from which inputs
Where
generate_predictions.py: 'model_version': predictor.model_version or 'current' (always 'current'); features_json never set
Effect
You can't compare models on live results or debug a bad pick. The AI prompt's "Feature Summary" section is always empty, and it looks up names like home_ppg that the feature builder never produces.
Fix
Save predictor.trainer.version and a compact features_json on every prediction.
ML-13LowTraining hygiene
What
No early stopping (eval_set is passed but early_stopping_rounds isn't). The use_label_encoder parameter is deprecated. The three models refit the shared scaler (harmless today, fragile later). Trees don't need scaling at all. The unused settings.ML_CONFIG parameters differ from the ones actually used.
ML-14LowConfidence bands differ from screen to screen
What
Prediction.save: strong ≥ 70%, moderate ≥ 55%. daily_picks: ≥ 55%, "low risk" ≥ 60%. stats: high ≥ 60%, medium ≥ 45%. Predictions page "High confidence" filter: ≥ 70%. The same pick can be "moderate", "low risk" and "high" on different screens. Draws are almost never the top probability, so the app almost never predicts a draw. That is expected, but should be explained.
Fix
One shared set of bands (a backend constant exposed via model_info), used by every page.
