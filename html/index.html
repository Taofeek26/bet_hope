Bet Hope — full system audit

This audit covers AWS infrastructure and cost, the prediction model, the data sources, every backend endpoint, and every page, tab and button in the frontend, down to colours and logos. Each finding says where it lives in the code, what goes wrong for the user, and how to fix it.

Audited 29 Sep 2026 · commit 75165fd (main) · Next.js 14 frontend (Vercel) · Django + Lambda + API Gateway + RDS backend (AWS SAM)

What this audit could and could not check. I read the code, the SAM template, the CI workflow and the model files saved in backend/models/. I had no access to the AWS bill, the AWS console, the live API or the production database. No builds or tests were run. So the cost figures are estimates from AWS list prices, and a few runtime effects are marked likely in the finding. The verification commands let you confirm each one against your real account.

How the system fits together today

  1. Frontend: Next.js 14 on Vercel. It calls the API directly through NEXT_PUBLIC_API_URL and polls several endpoints on timers (every 15 s, 60 s and 5 min).
  2. API: API Gateway (REST, 29-second limit) → bet-hope-web Lambda (1 GB, Django via apig-wsgi), running inside a private VPC subnet.
  3. Jobs: EventBridge rules → bet-hope-manage Lambda (2 GB, 15 min). The jobs are: 04:15 sync fixtures and results (football-data.org) and predict + validate; 05:00 retrain; 05:15 predict again.
  4. Database: RDS Postgres db.t4g.micro in private subnets. It is stopped every day at 16:00 UTC and started at 04:00 UTC by bet-hope-infra-toggle.
  5. Internet access from the VPC: a NAT Gateway, created at 04:00 and deleted at 16:00 each day. It is needed only because the Lambdas sit inside the VPC to reach RDS.
  6. Model storage: S3 bucket (versioned) plus a ModelVersion row in Postgres marking the active model.
  7. AI analysis: OpenRouter deepseek/deepseek-v4-pro, called synchronously inside the 29-second web request.
