Decisions

D1Option A: keep Lambda, drop the VPC, use Neon Postgres
Chose
Lambdas run outside any VPC and connect to a managed Postgres over TLS. Neon is the default. Supabase works the same way; only the connection string differs (see step 1).
Why
It's the smallest change: same SAM stack, same CI, same API URL, same code. It removes the NAT Gateway, the RDS instance and the daily start/stop toggle, and with them the 12-hour daily outage. Neon supports pgvector and scales to zero.
Rejected
Option B (one server) means more ops work and a new deploy path. Option C (PaaS) means a new platform and a higher bill as usage grows. Both are still valid later.
Cost
Removes the ~$16/month NAT, ~$2 EIP and ~$8–10 RDS. Neon's free tier covers up to 0.5 GB (step 4 measures your size). Its paid tier is usage-based, from about $5/month.
D2Two-stage cutover with a rollback copy
Chose
A new template parameter LegacyNetwork (keep / remove). All 26 old network, RDS and toggle resources carry Condition: KeepLegacy. Stage 1 (keep) moves the app to Neon but leaves RDS in place as an untouched copy. Stage 2 (remove) deletes the old resources, and RDS takes a final snapshot first (DeletionPolicy: Snapshot, already in the template).
Why
If anything is wrong after the switch, rollback is one redeploy. Detaching Lambdas from a VPC also releases their network interfaces slowly, so deleting subnets and security groups in the same deploy often fails. Two stages avoid that.
D3A separate, slim requirements file for the Lambda image
Chose
backend/requirements-lambda.txt, used only by Dockerfile.lambda-web. The full requirements.txt is untouched for Docker Compose.
Removed
torch, sentence-transformers, transformers, huggingface-hub, tiktoken, google-generativeai, optuna, redis, django-redis, gunicorn, uvicorn, aiohttp, httpx, pydantic, structlog, python-json-logger, Pillow, python-slugify, drf-spectacular, django-extensions, django-allauth. The system compilers (gcc, postgresql-devel) are gone too. xgboost became xgboost-cpu: the same library and model files, without the bundled CUDA/NCCL.
Why it's safe
I listed every module the backend imports (command log #1–#2). The removed ones are either never imported, or imported inside a try/except (google, optuna, understat, sentence_transformers). Local embeddings could never have worked here anyway: the local model makes 384-number vectors, and the database column holds 1536.
Result
All dependencies now total 115 MB of compressed Linux wheels (command log #14), with no torch or CUDA.
D4A .dockerignore for the backend
Why
COPY . . was copying about 242 MB of old model pickles committed to git (backend/models/, cache/, data/) into every image. On Lambda, models load from S3 into /tmp, so the copies were dead weight. Docker Compose mounts the folder directly, so it's unaffected.
Later
Removing those pickles from git history is a separate cleanup and isn't done here.
D5Copy the data with a Django command run inside the manage Lambda
Why
RDS sits in private subnets with no route from the internet, so you can't pg_dump it from your laptop, and the image has no pg_dump binary. The manage Lambda can reach RDS (it's in the VPC) and the internet (through the NAT, 04:00–16:00 UTC), so it can stream one database into the other.
How
The new copy_database command does five things. It reports sizes, creates pgvector on the target, and runs migrate there. It then copies every table with streaming COPY in one transaction and resets id sequences. Finally it compares row counts and fails loudly on any mismatch. It never writes to the source. It refuses to run without --yes-overwrite-target, and refuses if the target is the source.
Rejected
Starting empty and re-syncing: the full historical import takes longer than the 15-minute Lambda limit, and you'd lose prediction history and task logs.
D6AI analysis runs in the background; the browser polls
Chose
POST /ai-recommendations/generate/ creates a pending row and invokes the manage Lambda asynchronously (the same mechanism as the admin task runner), then returns 202 with the id. The new generate_ai_recommendation command fills in the row. The UI polls GET /ai-recommendations/{id}/ every 3 s, for up to 4 minutes. A second click within 5 minutes reuses the pending job instead of paying for another LLM call. Without MANAGE_FUNCTION_NAME (local development), the old inline behaviour is kept.
Rejected
A Lambda Function URL, which would mean a second API URL, new CORS rules and new auth surface. A faster model would change output quality, which is your call and isn't part of this phase.
D7Database connection settings for a managed, pooled Postgres
Chose
connect_timeout=5 (DB_CONNECT_TIMEOUT), CONN_MAX_AGE=0 (DB_CONN_MAX_AGE), DISABLE_SERVER_SIDE_CURSORS=True (DB_DISABLE_SERVER_SIDE_CURSORS). SSL comes from ?sslmode=require in the URL.
Why
With a timeout, an unreachable database fails in about 5 s instead of burning 29 s of Lambda time (tested: command log #11). Not holding connections open lets Neon suspend when idle. Neon's pooler (PgBouncer, transaction mode) can't keep the server-side cursors Django uses for .iterator(). /health/ now runs SELECT 1 and returns 503 when the database is down, without echoing the database host.
D8Create the pgvector extension in a migration
Why
The extension was only created by scripts/init_db.sql (Docker), so migrate on any fresh database failed. I prepended VectorExtension() to documents/0001_initial.py. Databases that already applied that migration don't re-run it, so nothing changes for them.
D9Set log retention and ECR clean-up with the CLI, not the template
Why
The log groups and the ECR repository already exist outside the stack. Declaring them in the template makes CloudFormation try to create them, and the deploy fails with "already exists". Two CLI calls (step 6) do the same job.

Runbook: what you run, in order

Timing: steps 3–5 must run while the NAT is up and no scheduled job is writing: between 05:30 and 15:30 UTC (06:30–16:30 WAT). Do steps 4–5 back to back. Anything written to RDS after the copy (e.g. that day's 05:00 training) isn't carried over.
Learned during the Phase 0 deploy:
  • AWS CLI v1: your CLI is version 1 (1.44.39). Remove --cli-binary-format raw-in-base64-out from every aws lambda invoke below; v1 sends the payload as-is.
  • Rollback by digest, not latest: the Lambdas used to point at latest, which moves on every build. Step 3's saved image reference is now an explicit tag. Keep using the file it writes.
  • Already done in Phase 0: the app code for this phase is already live (image 11a47c9), which covers async AI, the health check and the copy tool. Step 2 (build) and step 3 (manage image) are already done. Set IMAGE_URI=294983767092.dkr.ecr.us-east-1.amazonaws.com/bet-hope-web:11a47c9a3078fea0fe1e21246c5538a2d69c6823 and start at step 4.
  • Frontend deploys aren't automatic: Vercel isn't connected to git. Phase 1 has no frontend change beyond what Phase 0 already deployed, so nothing to do there.

Step 1: create the Neon database

  1. Go to neon.tech → New project → Postgres 16 → region AWS US East 1 (N. Virginia), the same region as the Lambdas.
  2. Dashboard → Connect. Copy two connection strings:
    • Direct (connection pooling off). Used once, for the copy. Save it as NEON_DIRECT_URL.
    • Pooled (pooling on; the host contains -pooler). Used by the app. Save it as NEON_POOLED_URL.
    Both must end with ?sslmode=require. Keep them in your local secrets file, not in git.

Using Supabase instead: its direct host is IPv6-only on the free tier, and Lambda outside a VPC is IPv4. Use the Session pooler string (port 5432) for the copy and the Transaction pooler string (port 6543) for the app.

export NEON_DIRECT_URL='postgresql://…@ep-xxxx.us-east-1.aws.neon.tech/neondb?sslmode=require'
export NEON_POOLED_URL='postgresql://…@ep-xxxx-pooler.us-east-1.aws.neon.tech/neondb?sslmode=require'

Rollback: none needed. Nothing uses it yet.

Step 5: copy RDS into Neon

The payload goes in a file, so the database password doesn't end up in your shell history. Delete the file afterwards.

python3 - <<'EOF'
import json, os
json.dump({"command": "copy_database",
           "args": ["--target-url", os.environ["NEON_DIRECT_URL"], "--yes-overwrite-target"]},
          open("/tmp/copy.json", "w"))
EOF
aws lambda invoke --function-name bet-hope-manage --cli-read-timeout 900 \
  --cli-binary-format raw-in-base64-out --payload file:///tmp/copy.json /tmp/copy-out.json
rm /tmp/copy.json
python3 -c "import json;d=json.load(open('/tmp/copy-out.json'));print(d['status']);print(d['stdout'][-1500:]);print(d['stderr'][-1500:])"

Expect: success and "Done: N tables copied, row counts match." On error or timeout, don't continue. The stderr text says which table failed. The copy is safe to re-run.

Rollback: not needed. RDS was only read.
