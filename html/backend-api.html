API findings

API-01CriticalThe rate limit is lower than the app's own polling
Where
base.py DEFAULT_THROTTLE_RATES = {'anon': '100/hour'}, applied to every view; polling in hooks/useApi.ts
Math
With one dashboard tab open: live matches every 15 s (240/hour), upcoming every 60 s (60/hour), daily picks ×2 and task status every 5 minutes (about 36/hour). That's roughly 330 requests per hour, before page loads. Each loaded prediction card also fires one AI lookup. The 101st request in an hour gets HTTP 429 and the UI shows "Failed to load". The throttle counter is kept in per-container memory (LocMemCache), so how soon it hits varies from minute to minute.
Correction (30 Sep)
The Phase 0 live test showed the limit rarely triggered in practice. Behind the edge-optimized API, DRF keyed visitors on a header that changes per request, so the counters never added up (P0-D9). The polling waste was real, but "429 after ~15 minutes" was overstated. Fixed in Phase 0 together with the identity problem.
Fix
Raise anonymous read limits (e.g. 2000/hour) with a separate strict scope for expensive endpoints (AI, generate). Cut polling: no live polling until DATA-05 is fixed, and 5 minutes for the rest. Load AI analysis only when the user expands a card.
API-02MediumThe league stats and "current season" filter always crash
Where
views/leagues.py stats and SeasonViewSet.get_queryset: Season.objects.filter(is_current=True)
Why
is_current is a Python @property, not a database column, so the filter raises FieldError. In stats, F is also used before its import inside the function, which would raise UnboundLocalError.
Fix
Filter with code=league.current_season and move the import to the top of the file.
API-03MediumThe head-to-head endpoint uses field names that don't exist
Where
views/teams.py head_to_head and HeadToHeadSerializer use team1/team2/team1_wins…; the model has team_a/team_b/team_a_wins…
Fix
Compute head-to-head directly from Match (the view already queries those matches) and drop the empty HeadToHead table.
API-04HighAI analysis runs longer than API Gateway allows
Where
ai_recommendation_service.py: deepseek/deepseek-v4-pro, max_tokens=4000, called synchronously; API Gateway and WebFunction Timeout: 29
Effect
Reasoning models spend many tokens "thinking" before answering. When the call passes about 29 s, the browser gets a 504 and shows "Failed to generate AI analysis" (the frontend's 120 s timeout never comes into play). The OpenRouter call may still finish and be billed, and when it does, its result is saved without the user seeing it.
Fix
Make generation asynchronous: create an AIRecommendation row with status pending, invoke the manage Lambda (already used for admin tasks), and have the UI poll. Alternatively, use a Lambda Function URL, which has no 29 s cap, or a faster non-reasoning model with max_tokens≈600. Also cache: one analysis per prediction per model version.
API-05MediumA GET request can create a prediction, and crashes if a match has two
Where
views/matches.py prediction: Prediction.objects.get(match=match); on DoesNotExist it generates and saves one
Why
Prediction.match is a ForeignKey, and --historical and the simple fallback use create(), so a match can have several. .get() then raises an uncaught MultipleObjectsReturned (500). Writing on GET also lets crawlers generate predictions, including for finished matches.
Fix
Use .order_by('-created_at').first(), don't generate on GET, and add a unique constraint (one live prediction per match per model version).
API-06Low/matches/with_predictions/ always returns prediction: null
Where
UpcomingMatchSerializer.get_prediction checks hasattr(obj, 'prediction'); the relation is named predictions
API-07HighLists silently stop at 20 items
Where
PAGE_SIZE: 20; extractResults() in lib/api.ts returns data.results and ignores next
Effect
On a busy Saturday the Predictions page shows only 20 of perhaps 100+ matches, in arbitrary order within the day. Its own "page 1 of N" control then pages through those 20. The Leagues page and the league filter drop leagues past #20.
Fix
Add a ?page_size= override (with a max) and have the frontend request by date with real server-side pagination. Order by kickoff, then league.
API-08MediumThe /sync/* endpoints and task-status pill are left over from the Celery setup
Where
views/sync.py
Why
The sync actions need API_FOOTBALL_KEY and call .delay(), which runs synchronously on Lambda (CELERY_TASK_ALWAYS_EAGER) inside the 29 s limit. task_status reads Celery's TaskResult table and beat schedule, which nothing writes on Lambda. So the header pill always says "0/18 Tasks · Never run", even when the EventBridge jobs succeed.
Fix
Replace task_status with a view over the TaskRun table, and have scheduled runs create TaskRun rows too. Delete the Celery-based sync actions.
API-09LowThe league list runs about 80 count queries per request
Where
LeagueSerializer: 4 SerializerMethodField counts per league (matches and predictions across all seasons)
Fix
Annotate the counts in the queryset once, or cache the payload for 10 minutes.
API-10LowA team's "upcoming" list returns the furthest fixtures, not the next ones
Where
views/teams.py fixtures: the queryset is ordered -match_date and upcoming is sliced from it
Fix
Order the upcoming list by match_date ascending.
API-11LowDead and confusing configuration
What
config/settings/lambda_settings.py (with CORS_ALLOW_ALL_ORIGINS = True) is never loaded; DJANGO_ENV=production selects production.py. next.config.js rewrites /api/* to ${NEXT_PUBLIC_API_URL}/api/v1/*, but axios already calls NEXT_PUBLIC_API_URL directly. If that variable ends in /api/v1 (as .env.example shows), the rewrite target would be …/api/v1/api/v1. It's harmless today and confusing later. The unused Celery, Redis and allauth apps are also still installed.

Security findings

SEC-01HighPaid and write endpoints are open to anyone
Where
AIRecommendationViewSet, DocumentViewSet (full create/update/delete), PredictionViewSet.generate/batch: all permission_classes = [AllowAny]
Risk
Anyone who finds the API URL (it's visible in the browser) can loop /ai-recommendations/generate/ and spend your OpenRouter balance. They can also edit or delete the knowledge-base documents that feed the AI prompt (prompt injection), trigger scraping and embedding jobs, and run unbounded batch predictions.
Fix
Documents and batch: IsAdminUser. AI generate: a per-IP throttle (e.g. 5/hour), return the cached result if one exists, and a daily spend cap in code. Set a spending limit on the OpenRouter key as well.
SEC-02MediumSecrets are stored as plain Lambda environment variables
Where
template.yaml: DATABASE_URL contains the DB password; DJANGO_SECRET_KEY and all API keys are passed as plain env vars on both functions
Risk
Anyone with lambda:GetFunctionConfiguration can read them. They also sit in plain text in infrastructure/*.local.txt. Those files are git-ignored, which is good, but they're on disk.
Fix
Store them in SSM Parameter Store (SecureString; the standard tier is free) and read them at cold start. Rotate the DB password and API keys after moving.
SEC-03MediumThe admin task runner allows --clear
Where
serializers/tasks.py ALLOWED_ARGS: sync_data and generate_predictions both accept --clear
Risk
sync_real_data --clear deletes every league, team, match, odds row and prediction. One mistaken API call from a stolen admin token wipes the database.
Fix
Remove --clear from the allowed list. Keep destructive operations CLI-only.
SEC-04MediumThe admin session silently breaks after 60 minutes
Where
SIMPLE_JWT access lifetime is 60 min; admin/page.tsx stores only the access token in localStorage and never refreshes; the 401 interceptor removes the token but the page state still shows "signed in"
Effect
After an hour, the Run buttons do nothing. The error is only written to the browser console.
Fix
Store the refresh token and refresh on 401, or log out and show the sign-in form on 401. Show trigger errors in the page.
SEC-05LowBroad defaults
What
DJANGO_ALLOWED_HOSTS: "*"; API Gateway CORS AllowOrigin: '*' (Django's CORS list is stricter, but the two disagree); the public-read static bucket (COST-08); no security headers such as HSTS. The last point is acceptable behind API Gateway's HTTPS but worth setting.
"500" means the code raises an exception in that code path, found by reading the code. I didn't call the endpoints against the live API.
