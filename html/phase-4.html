Decisions

P4-D1Remove buttons that can't work rather than fake them
What
The bell, user menu and ☰ had no feature behind them. The app has no user accounts (Phase 0 locked the paid and write endpoints instead), so they were removed. Search was kept because a team search is genuinely useful and cheap. The support e-mail was removed because no such mailbox exists.
P4-D2"Status" means data freshness, not a task queue
Why
Since Phase 1 there is no Celery queue: jobs run on EventBridge schedules. The useful question is "is the data up to date?". Each job is compared with its schedule (26 h for daily jobs, 4.5 days for the Mon/Thu one) and reported as healthy, stale or unknown, in the same response shape, so the existing UI works unchanged.
P4-D3Favourites stay in the browser
Why
There are no accounts, and the existing useFavoritesStore already persists to local storage. Each favourite team loads its own details and next fixture. A team that no longer exists (e.g. merged in Phase 2) shows a "Remove" button instead of breaking the page.
P4-D4Team links inside clickable match cards
What
A link can't contain another link, so each match card is now a box with a card-wide link underneath, and the team names sit above it as their own links (the "stretched link" pattern). Clicking anywhere else still opens the match.

Not done in this phase

  • A lint rule for unknown Tailwind classes. The invented class names were fixed by hand. A guard (e.g. eslint-plugin-tailwindcss with no-custom-classname) would need its config tuned to the app's own CSS classes first.
  • A visual check in a real browser on a phone. Pages were type-checked, built and fetched (HTTP 200), but not screenshot-tested.
  • Nicknames in search ("Spurs", "Gunners"): search matches names and data-source aliases only. Add nicknames with record_alias if wanted.
